# Technical Decision Register

**Project:** Autonomous Cyber Deception Platform Using Reinforcement Learning for Adaptive Honeynet Orchestration  
**Purpose:** Record the project's current approved design decisions and distinguish them from experimental or unresolved parameters.

## 1. Decision status definitions

- **Approved** — part of the current project design; do not change without explicit agreement.
- **Approved baseline / experimental parameters** — the structure is retained, but numerical values or heuristics require evaluation and may change through a documented decision.
- **Open / verify before implementation** — insufficient evidence exists to hard-code a value or behaviour. Inspect the repository, captured fixtures, training artifacts, or pinned component version first.

## 4. Reinforcement-learning state and action decisions

### 4.1 State representation

The six-feature schema and total state count are retained from the project design:

| Feature | Cardinality | Values |
|---|---:|---|
| Threat Tier | 3 | `LOW`, `MEDIUM`, `HIGH` |
| Session Phase | 3 | `RECON`, `EXPLOIT`, `PERSIST` |
| Attacker Profile | 2 | `AUTOMATED`, `HUMAN` (UI wording may be Automated-like / Interactive-like) |
| Behavioral Risk | 2 | `SAFE`, `RISKY` |
| Engagement Depth | 2 | `SHALLOW`, `DEEP` |
| Model Confidence | 2 | `LOW`, `HIGH` |

The full state space is `3 × 3 × 2 × 2 × 2 × 2 = 144` states. The implementation must use deterministic encoding and only return valid state IDs `0–143`.

| ID | Initial rule/threshold | Status / caution |
|---|---|---|
| D-020 | Threat tier initial bins: LOW if risk `R < 0.3`; MEDIUM if `0.3 <= R < 0.7`; HIGH if `R >= 0.7` or a documented hard-high-risk indicator applies. | Approved baseline / experimental. Calibrate `R`; high `Harmless` probability is not high threat. |
| D-021 | Session phase: Discovery→RECON; Execution/Impact→EXPLOIT; Persistence/Defense Evasion→PERSIST. For Other/Harmless, preserve last reliable phase or use an explicitly documented fallback. | Approved mapping; fallback details must be documented. |
| D-022 | Attacker profile uses AUTOMATED/HUMAN categories. A command rate above 10/minute is only a heuristic. | Approved baseline / experimental; do not claim it proves human or automated identity. |
| D-023 | Engagement depth is SHALLOW if duration `<60s` OR command count `<5`; DEEP if duration `>=60s` AND command count `>=5`. | Approved baseline / experimental. |
| D-024 | Initial model-confidence threshold is `0.7`. | Approved baseline / experimental; define the exact confidence calculation for multi-label output before use. |
| D-025 | Behavioral risk is based on observed attempts/events. Cowrie commands execute in its emulated shell, not on the Ubuntu host. | Approved principle; exact risk rules require tests. |

### 4.2 Action IDs

The nine approved action IDs and intended semantics are:

| ID | Action | Required meaning / restriction |
|---:|---|---|
| 0 | No-op | Keep the exact current profile unchanged; no profile mutation. |
| 1 | Return-to-safe-profile | Restore a predefined safe baseline. This does not terminate or block the session. |
| 2 | Profile A — Default/Low-Interaction | Select the known baseline response profile, normally at session start. |
| 3 | Profile B — High-Engagement | Use a more responsive but still simulated output persona. |
| 4 | Profile C — Delayed Response | Apply a bounded, preconfigured delay; enforce a maximum. |
| 5 | Profile D — Decoy-Rich | Expose only predefined fake files and harmless synthetic contents. |
| 6 | Profile E — Verbose Output/Telemetry | Select an approved informative output/diagnostic profile. Global audit logging must remain enabled. |
| 7 | Profile F — Persona/Banner | Select a coherent, preconfigured per-session persona/banner where supported. |
| 8 | Profile G — Contextual Responses | Select from allowlisted command-response templates; no arbitrary shell execution. |

Do not conflate No-op (keep the current profile unchanged) with Profile A (explicitly select the default profile), or Return-to-safe (restore a restricted baseline after risk increases) with either of them.

## 5. Controller and containment decisions

| ID | Decision | Status | Implementation consequence |
|---|---|---|---|
| D-030 | The agent selects actions; a separate Controller validates and executes them. | Approved | Agent must not directly modify Cowrie or issue shell commands. |
| D-031 | Controller lifecycle distinguishes `requested`, `accepted`, `applied`, `rejected`, `failed`, and `expired`. | Approved | Never display `accepted` as `applied`. Store request and final result separately. |
| D-032 | A separate Safety Guard evaluates containment independently of DistilBERT and Q-learning. | Approved | Safety/containment continues to function if the classifier is unavailable. |
| D-033 | Containment triggers must be explicitly configured; they may use a risk threshold or explicit hard rule. | Open / configure before implementation | Do not hard-code an unapproved threshold. The previously discussed value `0.97` is an example, not a frozen project threshold. |
| D-034 | Firewall executor runs as a restricted systemd service inside Ubuntu and exposes only fixed operations over protected local IPC. | Approved | No arbitrary commands, arbitrary firewall text, Docker socket, `--privileged`, or broad `NET_ADMIN` grant to the app containers. |
| D-035 | Scope blocking to inbound traffic destined for the Cowrie published SSH service (TCP/2222), after validating the actual Docker/network path. | Approved | For Docker's iptables backend, validate the `DOCKER-USER` path and actual NAT/bridge details; do not assume UFW INPUT alone protects published ports. |
| D-036 | Per-session Cowrie disconnect and source-IP firewall blocking are separate operations. | Approved | Record and verify both results independently. A source-IP block affects subsequent connections to the scoped service from that IP. |

## 7. Phase 7-specific decisions

| ID | Decision | Status | Implementation consequence |
|---|---|---|---|
| D-050 | Cowrie's `session` value is the authoritative session key; source IP is an attribute, not the key. | Approved | Multiple sessions from one IP remain separate. |
| D-051 | Each ingested event has an internal unique `event_uid` and a separate content `raw_fingerprint`. | Approved | Do not use Cowrie's `eventid` as the unique record ID; do not deduplicate solely by content fingerprint. |
| D-052 | Preserve original timestamps and normalize timestamps to UTC ISO-8601. | Approved | Retain both original and normalized values. |
| D-053 | Preserve the complete raw JSON record and source event type. | Approved | Normalized data must remain traceable to the source line. |
| D-054 | Reconstruct `full_session` from cumulative command-input events in the exact training-compatible format. | Approved requirement; exact text-building rule open | Inspect training preprocessing. Do not invent separators, tokenization, or cleaning. |
| D-055 | Session records are incremental and are persisted/updated as events arrive. | Approved | `full_session` is a current cumulative snapshot, not proof that the session is complete. |
| D-056 | A session closes on a verified Cowrie close event or an explicitly configured timeout policy. | Approved principle; timeout value open | Do not use inactivity alone as a closure signal without an explicit policy. |
| D-057 | The event follower must tolerate partial lines, malformed JSON, rotation, restart, late events and duplicate replay. | Approved | These cases are mandatory Phase 7 tests. |

## 8. Open items to resolve from the repository or evidence

Do not invent these values. Record the verified result in `README.md` or a follow-up decision entry:

1. Exact Cowrie Docker image tag/digest and version.
2. Exact deployed Python version and dependency versions.
3. The actual Cowrie command event field and complete set of event types used for command, download, connection, login, and closure handling.
4. The exact DistilBERT serving preprocessing and output contract from the training notebook/artifacts.
5. The exact `full_session` delimiter/cleaning/tokenization behaviour used during training.
6. The timeout value and operational policy, if timeout-based session closure is used.
7. The exact containment threshold/hard-rule configuration and verification/rollback policy.
8. The final API schemas, port bindings, and VM network/interface details.

## 9. Changing a decision

When a decision needs to change, add a dated entry containing: decision ID, old value, new value, reason, evidence/test, affected components, migration impact, and approver. Update the architecture and affected phase specification in the same change. Do not quietly edit an approved contract in code only.
